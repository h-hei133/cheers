## 1. 贯穿本阶段的两条取舍

### 1.1 「声明与行为不一致」优先于「缺功能」

本阶段的可做项里，两类都有：

| 类型 | 例子 | 读代码的人会怎么想 |
|---|---|---|
| **声明与行为不一致** | T1：`Explore` 声明 `disallowedTools: ["write","edit"]`，**无人执行** | 「这个子代理不能改文件」——**错的** |
| **缺功能** | D1：子代理不跑 agent 循环 | 「子代理能力弱」——**对的** |

**前者优先**。理由：缺功能是**已知的边界**，声明不一致是**误导**。
`AGENTS.md` 要求「不得把失败伪装成成功态」，而**声明一个不存在的边界是同一类问题**。

**T1 因此排第一，且它是安全相关**——`Explore` 的定位是「只读探索」，
若它能 write，那么「派一个 Explore 去安全地看看」这个用法就是**假的**。

### 1.2 「绕过 provider 层」是**回归**，不只是缺陷

Phase 11 修了四项与 provider 层相关的能力（T2 流内 error、T4 失败分类、
T5 temperature 门控、T6 `budget_tokens`）。**这四项在 `task` 与 `/btw` 上全部无效**：

| Phase 11 修的 | `task` 是否受益 | 证据 |
|---|---|---|
| T5 temperature 门控 | ❌ | `taskTool.ts:160` 硬编码 `temperature: 0.3` |
| T6 `budget_tokens` | ❌ | 不发 `thinking` |
| T4 `failureClass` | ❌ | 只报 `The provider answered ${res.status}` |
| T2 流内 error 检测 | ❌ | 用非流式 `res.json()` |

**即**：Phase 11 的修复**有两条路径没覆盖**。
这正是复核轮 6 个缺陷的同一个共性（「修了一处，漏了兄弟」）的**放大版**——
这里是**整条调用路径**被漏掉。**T2 因此排第二。**

### 1.3 复核更正：**T1 单独做是空转**（`V8Decisions` 提出，主代理核实成立）

**子代理原判**：「T1 在 `taskTool` 不跑循环、不传工具的前提下，过滤的是**空集**。」

**主代理核实**：读 `taskTool.ts:148-162` 的请求体：

```js
body: JSON.stringify({
  model,
  messages: [ {role:"system",...}, {role:"user",...} ],
  temperature: 0.3,
}),                       // ← 没有 tools 字段
```

**`grep -n 'tools' taskTool.ts` 只命中 1 处，且是 `import type { ToolDefinition }`**。
即 **`task` 的子代理调用根本不传工具**——子代理**没有工具可用**。

**因此**：T1（「让声明的工具边界生效」）在**当前状态下过滤的是一个空集**，
`Explore` 声明 `disallowedTools: ["write","edit"]`，而子代理**本来就不能 write**——
不是因为它被拦住，是因为**它没有任何工具**。

**结论：T1 不能独立施工，必须与 D1 捆绑。**

| 旧排序 | 更正后 |
|---|---|
| T1（P0，独立）→ T2 → T3 → D1 | **T2**（P0，可独立）→ **T3** → **D1+T1 捆绑** → T4/T5 |

**为什么 T2 仍可独立**：它改的是**请求怎么发**（走 provider 层），
与子代理有没有工具无关——`/btw` 同样受益。

**为什么 T3 要在 D1 之前**：worktree 的自动合并语义在子代理**还不能改文件**时无害，
**一旦 D1 让它能改文件，自动合并就是「无审查地把改动并入主工作区」**。
所以 T3 是 D1 的**安全前置**。

**这修正了 §1.1 的推论**：原文说「声明与行为不一致优先于缺功能」——
方向对，但**在 T1 这个例子上，两者不可分离**：
只有先让子代理**有工具**（D1），才谈得上**限制工具**（T1）。

### 2.2 D2 — 数据驱动权限规则（含 deny）→ **维护者裁定：做**（最小 deny + 可选 pattern）

> **复核更正（2026-09-26）**：本节原建议「只补 deny，不做路径/正则」，
> 并引用 pi 的哲学作为依据。**子代理 `V8Decisions` 指出两处问题，主代理核实后采纳其一、部分采纳其二。**

**更正一：引用 pi 的方式错了（采纳）。** 原文说「pi 反对的是靠审查保安全，
不是提供拒绝能力」——**这个解读把 pi 的论点窄化了**。读 pi `docs/security.md:1-20`：

> "Safety comes from limiting the files, credentials, processes, and network services Pi can
> access and affect if a generated action is wrong or hostile. **Watching the transcript, using
> project trust, and reviewing changes do not create a security boundary.**"

**pi 说的是「审查/信任/看记录都不构成安全边界」**，针对的是**prompt injection 与不可信代码**，
**它根本没有讨论「用户想配置拒绝某工具」这件事**。所以**用 pi 的哲学反对 deny 是错误引用**。
**pi 的立场对本裁决点中立**——它既不禁忌 deny，也不支持。

**更正二：路径级粒度不能省略（部分采纳）。** 原文说「不做路径/正则，收益不明确」。
**核实参考**：opencode 的规则**是** pattern 化的——

```ts
// packages/schema/src/v1/permission.ts:19-22
export const Rule = Schema.Struct({
  permission: Schema.String,
  pattern: Schema.String,      // ← 有 pattern
  action: Action,              // "allow" | "deny" | "ask"
})
```

**即参考的 deny 不是「禁用某工具」，是「禁用某工具在某 pattern 上的调用」。**
而用户真正想防的往往是**具体的高危目标**（`bash` 对某路径、`read` 对凭据文件），
**不是整个工具**——粗粒度的 deny 满足不了这个需求。**这一点原文用一句话跳过了，是真实取舍。**

**但仍保留「不做完整规则表」的结论**，理由改为：
① 完整规则表的主要成本在**匹配语义**（相对路径、符号链接、glob 方言）与**优先级规则**
   （allow 与 deny 同时命中时谁赢），这是**独立的复杂子系统**；
② 我们的 `evaluator.ts` **目前连 deny 的存储都没有**（`:156` 的 `deny` 只用于 plan 模式硬阻断），
   所以第一步不是做规则表，而是**让 deny 这个概念存在**；
③ 先做**最小可用的 deny**（工具级 + 可选 pattern），**实测用户是否真的需要 pattern**，
   再决定是否扩展到完整规则表。

**三个选项**（据更正后重写）：

| 选项 | 内容 | 成本 |
|---|---|---|
| **(a) 完整规则表** | 照参考：`{permission, pattern, action}` + 匹配语义 + 优先级 | **高** |
| **(b) 最小 deny** | `{tool, pattern?}` 的 deny 列表，**绕过免疫**，pattern 可选且支持简单的路径前缀 | **中** |
| **(c) 维持现状** | 承认「审查不构成安全边界」，精力放在进程/文件边界 | **零** |

**建议 (b)**。理由：
① 用户**确实需要「永远不许」的表达**——这是功能缺口，与 pi 的哲学**无关**（见更正一）；
② **保留 pattern**（可选、简单形式），因为参考证明了它有用（见更正二）；
③ 不做完整规则表，因为匹配语义与优先级是独立子系统，**应等实测证明需要再建**。

**若选 (b)，必须满足**：deny **绕过免疫**——不能通过审批被放行。
否则它就是一个「建议」，与 T1 要修的「声明不生效」是同一类问题。

### 2.3 D3 — `cheers.json` / `.agents/settings.json` → **维护者裁定：删除两份**

**决定性证据**（前置 §5.4）：这**不是「未被读取的配置」**，是**另一个 schema 的草稿**。

- 读取器的候选路径是 `config.json` 与 **`.cheers.json`（有点）**，
  **`cheers.json`（无点）不在其中**；
- 真实 schema 是**扁平**的（`.cheers.example.json`：`{"provider": "...", "maxTurns": 6}`），
  而 `cheers.json` 是**嵌套**的 `settings.v1`；
- **`model` 字段类型冲突**：读取器当**字符串**（`runtimeConfig.ts:72`），
  文件里是**对象**。**即使改名也无法解析。**

**逐字段核实**：`maxTurns`/`mcpServers`/`altScreen`/`showThinking` **都有实现**（用另一套 schema 表达）；
只有 `permissions.allowRules`（全仓 0 引用）与 `skills.directory`（`.codex/skills` 不存在）是空头支票。

**三个选项**：

| 选项 | 内容 |
|---|---|
| **(a) 删除两份** | 它们是零读者、逐字节重复、含外部项目名（`.codex/skills`）的**异 schema 草稿** |
| **(b) 实现 `settings.v1`** | 工作量中：一套新 schema + 读取器，其中 `allowRules` 与 `skills` **是未实现的功能** |
| **(c) 标记为草稿** | 保留但加注释。**留着不读的权威配置仍是误导** |

**建议 (a)**。理由：
① **不是「差一根线」**——schema 形状与字段类型都冲突，说明它是**另一份设计**；
② 删除**不会**删掉待实现的功能——`allowRules` 与 `skills` **从未按这个 schema 设计过**
   （D2 若选 (b) 会用**配置的**形式实现，不是这个文件）；
③ 留着会让用户以为改了有用——**静默失效的配置契约**，与 08 `T2` 的原始问题同类；
④ 含外部项目名且路径不存在，**违反 `AGENTS.md`**。

**⑤ 决定性证据（本轮新增）：它们指向的 schema 根本不存在。**


**`settings.v1.json` 从未被写出来。** 两份文件声明遵循一个**不存在的契约**——
这比「未被读取的配置」更彻底：**它们连自己声明的规范都没有。**

> **复核记录（2026-09-26）**：子代理 `V8Decisions` 认为删除是「用清除草稿为借口
> 实质放弃已声明的契约意图」，建议「迁移为明确的 TODO 而不是假装从未有过」。
> **主代理不采纳这个结论，但采纳它的关切**：**会丢失「权限规则」与「技能目录」
> 这两个意图的记录**。故在 §8 的「意图登记」中保留这两项，
> 使删除**不丢失意图**——这才是该关切的正解，而不是留着一个指向不存在 schema 的文件。

### 2.4 D4 — 压缩后恢复工作文件（M8）→ **结论改为「做」**

> **维护者指示**：「利用 tinyfish 再去网上看看有没有相关资讯，本地上这个（Claude Code 副本）
> 有点老旧了。」**核实：确实过时**——本地副本是 v2.1.88，官方文档反映到 v2.1.198。
> **新证据改变了结论**：由「先度量」改为「**做最小版本**」。证据见前置 §9。

#### 现状（我们的）

压缩按 `keepRecentTokens` 从尾部保留（`compaction.ts:211-256` 的 `locateCut`），
**丢掉的中间部分包含文件内容**，且**压缩后不注入任何东西**——
`onCompact`（`compaction.ts:640`）只记录摘要与计数，**不恢复状态**。

#### 官方文档说了什么（**权威来源**）

`code.claude.com/docs/en/context-window` 的原文：

> Right after compaction, Claude Code re-reads up to five of the files Claude has read **or
> edited** in the session, choosing the ones **modified most recently**. A file over 5,000
> tokens comes back as **a path reference without its content**, shown as `Referenced file`
> instead of `Read`.

#### **关键发现：我们不需要做参考做的一半**

| 参考的恢复项 | 我们 | 依据 |
|---|---|---|
| 项目根指令文件（`CLAUDE.md`） | ✅ **天然存活** | 指令进**系统提示**，而系统提示**每次请求重建**（`cliRuntimeInvocation.ts:355,454,614`） |
| 技能正文 | ✅ **天然存活** | 技能同样进系统提示（`prompt.ts:95` 的 `sections.push(context.skills)`） |
| Git 状态快照 | ✅ 每请求重建 | 同系统提示路径 |
| plan 计划 | ⚠️ 有 plan 模式，无恢复 | **未登记**（见下「顺带」） |
| 后台任务提醒 | ❌ 无后台执行 | D6 不做，**不适用** |
| **读过/改过的文件** | ❌ **完全没有** | **本项要解决的** |

**即**：参考表里的恢复项**多数我们天然满足**（指令与技能在系统提示里，压缩碰不到它们）。
**真正的缺口只有「读过/改过的文件」。**

#### **第二个关键发现：「只回路径」是参考对大文件的既有行为**

原建议「只记文件名」曾被我自己判为「折中、收益推定」。
**新证据表明它不是折中**——参考**对大文件（>5000 token）就是只回路径不回内容**，
显示为 `Referenced file` 而非 `Read`。

**即**：路径引用是**参考的一等机制**，不是权宜之计。

#### 我们的接缝（成本比原估计低）

**已有**：`readCache.ts`（T11 新增）按 `{offset, limit, modifiedMs}` 记录已读文件。
**缺**：① **读取时间戳**（用于按「最近修改」排序）；② 「**改过的**」标记（参考包含编辑过的文件）。

**不需要**：内容存储——最小版本只回路径。
**不需要**：新状态子系统——扩展既有 `readCache` 即可。

#### 三个选项（据新证据重写）

| 选项 | 内容 | 成本 | 风险 |
|---|---|---|---|

### 2.5 D5 — 中途换模型（D11）→ **维护者裁定：不做**

**维护者裁定（2026-09-26）**：
> 「这个 D5 中途换模型是什么意思？是在某一个模型执行过程中切换吗？还是在一个 session 中切换模型？
> **如果是某一个模型执行过程中切换模型，那确实不做。**」

**先澄清术语**（这决定了裁定的适用性）：

**不存在「某个模型执行过程中切换」**——一次推理进行到一半换模型技术上没有意义。
准确说 D11 指的是**第三种情况**：**在同一个回合（turn）内，第 N 步之后换模型跑第 N+1 步**。

**三个层次的区分**：

| 层次 | 含义 | 我们是否支持 | 裁决 |
|---|---|---|---|
| **推理中途** | 一次模型调用进行到一半换模型 | **不可能**（无意义） | — |
| **回合内、步之间** | 同一回合内第 N 步后换模型 | ❌ 不支持（`NextStepUpdate` 只有 `messages`，`loop.ts:66-68`） | **D11 指这个** |
| **会话级** | `/model` 换模型，下次会话生效 | ✅ **已支持**（`modelCommandRuntime.ts:114,131` 写配置；会话运行时在 bootstrap 构造一次） | **已有** |

**裁定：不做。**

**理由**：
① 维护者已裁定不做（本项按裁定执行）；
② 从技术上看，D11 与「推理中途切换」是同一类**无真实用例的复杂度**——
   参考项目支持它，但我们的使用模式里**没有「廉价规划 → 昂贵执行」的分层需求**
   （全仓无 `cheapModel`/`plannerModel`/`modelTier` 概念）；
③ **会话级切换已经满足真实需求**（`/model`），
   而「回合内换模型」是**同一需求的更细粒度实现**，在没有场景的情况下不值得做；
④ `NextStepUpdate` 加字段是**非破坏性**的，所以将来要加**不需要现在预留**。

**若将来出现具体场景**（什么情况下必须在回合中途换），再按那时的证据做。

### 2.6 D6 — 后台命令执行（M2）→ **维护者裁定：采纳「本轮不做」**

**本轮新证据**：`processTree.ts` **已经**具备参考的对应物——
全局 detached 子进程 PID 追踪、Windows `taskkill /T` 级联、
POSIX `process.kill(-pid, "SIGKILL")` 进程组级联、
以及 SIGINT/SIGTERM/SIGHUP/exit 的自动处理器（`:8-11`）。

**即「孤儿进程」这个担心已不成立。**

**但**：`ambientFacts.ts:9` 明述「the shell has no detached execution mode」，
**连计数器都不放**。引入后台执行要**推翻这条明述的立场**，
并需要配套的工具（列出/停止后台任务）与通知注入机制。

**建议：本轮不做，但承认这是一个真实的能力缺口，并给出何时该做的判据。**

> **复核更正（2026-09-26）**：子代理 `V8Decisions` 指出——
> 原文把 `ambientFacts.ts` 的现状陈述当作「不可打破的架构戒律」，是**倒果为因**；
> 且把「需要配套通知机制」的实现复杂度偷换成了「推翻既有立场」。
> **主代理部分采纳**：`ambientFacts.ts:9` 确实只是**陈述现状**（「没有这个模式，所以不放计数器」），
> **不是戒律**。原文的措辞夸大了阻力。

**更正后的判断**：

| 事实 | 来源 | 对本裁决点的意义 |
|---|---|---|
| 孤儿进程清理**已具备** | `processTree.ts:8-11` 的进程组级联 + 信号处理器 | **技术风险不存在**——这是原文正确的一点 |
| 后台执行**是刚需**（长构建/长测试） | 参考都支持（Claude Code `run_in_background`） | **需求侧可能真实** |
| `ambientFacts.ts:9` 只是**陈述现状** | 原文读法 | **不构成阻力**——改了它就行，不是「推翻立场」 |

**即**：原文**高估了阻力、低估了需求**。真正的成本只有**实现复杂度**：
需要参数 + 配套工具（列出/停止）+ 通知注入。

**建议：本轮不做，理由是「没有用户需求证据」，而不是「有架构阻力」。**
判据：**若出现「一条命令跑得比会话超时长」的真实用例，就应做。**
**在拿到这个用例之前做，是为一组想象的需求写代码。**

**若维护者认为该做**，最小范围是：
① `bash` 加 `runInBackground` 参数；
② 一个「列出/停止后台任务」的工具；
③ 任务完成时把结果注入会话（这是**唯一**需要新机制的部分）。

**其余 4 处为措辞与依据的更正**（引用错误、夸大阻力、自相矛盾、表述不清），结论方向不变。

**教训**：**对抗性复核的价值在于它攻击的是「推理」而不是「事实」**。
`V7Claims` 验证事实（10/10 成立），`V8Decisions` 攻击推理（6 条中 5 条有效）。
**两类都要派**——只验事实会漏掉「事实都对但推论错了」的情况。

## 10. 子代理派遣纪律（**本轮教训，写入流程**）

**本轮 8 次派遣：3 个成功、5 个失败**（其中 3 个 429 零产出、2 个成功）。

| 类型 | 任务形态 | 成功率 |
|---|---|---|
| **封闭式取证** | 「读这 N 个文件，回答这 M 个问题」 | **高**（`RefClaude`/`RefOpencode` 都成功） |
| **端点探测** | 一条命令 | **高**（`Probe` 17 秒） |
| **开放式探索** | 「探索 X 的现状」 | **零**（3 个全部 429，各 20+ 次调用后耗尽） |

**原因**：429 在 **20+ 次工具调用后触发**，开放式任务必然在产出结论前耗尽额度。

**纪律**：
1. 任务书**必须限定读取预算**（「最多读 N 个文件」）并**要求提前 yield**；
2. **开放式探索不派子代理**——主代理自己核实更快且不会被限流；
3. 子代理的结论**必须逐条核验**（本轮 1 条推翻了旧记录、6 条改变了裁决）；
4. **事实类与推理类复核要分开派**——`V7Claims`（事实，10/10 成立）
   与 `V8Decisions`（推理，6 条中 5 条有效）**各有各的价值**。

## 12. 复核轮（**2026-09-26**）：本轮改动的六个漏洞

### 12.1 最重的一个：子代理的调用**不经过任何门禁**

**这是本轮自己引入的缺陷**，而且**我写的测试恰好绕过了它**——
deny 的测试只测了会话自己的 gate，就停在那里。

| 检查项 | 会话自己的调用 | 子代理的调用（修复前） |
|---|---|---|
| plan 模式 | ✅ | ❌ **可写文件** |
| 审批 scope | ✅ | ❌ |
| doom-loop 检测 | ✅ | ❌ |
| **用户的 deny 规则** | ✅ | ❌ |

**根因是两份手写的 gate 选项列表**：会话一份（`turn/session.ts`），子代理一份
（`entrypoints/cliRuntimeInvocation.ts`），**后者漏了 `denyRules`**。
测试失败信息 `expected [ 'bash', 'bash' ] to deeply equal []` 说明
**子代理真的执行了被拒绝的 `bash`**。

**修复不是补一个字段，而是消除重复**：
新增 `gateOptionsFor()` 作为**唯一**的选项来源，会话的 gate 与子代理的都从它派生；
子代理的 runner **由 turn 自己组装**（而不是由调用方传入），因为 gate 就在 turn 里，
**调用方再写一遍选项正是两份列表漂移的原因**。同时把 `beforeToolCall`/`afterToolCall`
传进子代理的循环——**修复前子代理的循环一个 hook 都没有**。
