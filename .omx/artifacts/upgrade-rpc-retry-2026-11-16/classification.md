The task is the current D.1 retry cancellation sub-batch. The whole D.1 command inventory and the other roadmap items remain pending by user request.

- `red.log`: five actual assertion failures against the original generic cancellation. Ordinary requests, commands, parent signals and queued successors were cancelled incorrectly. These are product failures, not provider failures.
- `green-first.log`: six gates and 3 suites / 51 tests passed at the first implementation. It predates the later wait fixtures and readiness-proxy repair, so it is historical evidence only.
- `waits-green.log`: 1 failed / 48 passed. The failed fixture assumed a body failure after accepted HTTP 200 should create a retry timer. The existing accepted-response contract forbids replay, as the adjacent step tests also assert. This is a fixture error. The fixture now uses a network failure before any response; an additional accepted-stream test checks in-flight no-op cancellation and a single failed request without replay. Production replay policy was preserved.
- `retry-accepted.log`: six gates and 11 suites / 372 tests passed. It predates the readiness-proxy repair and does not establish final compiled CLI cancellation.
- `retry-restored-build.log`: 3 suites / 59 tests, 2648 modules / 0 monoliths and build `29105ad640c0` passed. This is the original build used by the first native probe, not the final build.
- `retry-native-first.json` and matching driver/log: ordinary accepted stream passed, but provider cancellation failed after three refusal requests. The CLI readiness input proxy omitted the new cancellation method. This is a real product wiring defect, not a service or timing failure. `readiness-red.log` independently reproduced the same defect: expected one step, observed three. The repair delegates through the existing adopted input without buffering an early cancel for a later run.
- `retry-final.log`: final six gates, 14 suites / 412 tests, 2648 modules / 0 monoliths and build `754fdcb217b0` passed after the readiness repair. Final source snapshots match the current product bytes.
- `retry-reversals.json` plus `readiness-reversal.json`: five meaningful reversals each produced an actual AssertionError and exact byte restoration. The final `readiness-restored.log` confirms 4 suites / 67 tests passed after all restoration.
- `retry-native.json`: current build, Linux compiled CLI, six actual loopback POSTs passed. The local service induced both provider and outer backoff. Each cancelled backoff issued one request, reported failed and sent no second attempt; subsequent explicit prompts completed. Ordinary accepted stream and native shell command survived retry-only controls. An accepted stream's failed body stayed failed without replay. All clients produced valid JSONL and exited 0 at EOF.

In-flight retry control left the ordinary request live, idle cancellation was not buffered, and a subsequent explicit prompt completed. The observer records dispatch only; it does not inspect provider bodies. No real rate-limit or transport failure was induced. Original four configuration file hashes remained unchanged. The isolated catalogue retained the existing target identity because the original catalogue JSON is malformed; this does not prove the original malformed catalogue loads.
- `retry-docs.log`: strict binding-rule/docs gate and diff check passed; 119 existing advisory source references remain. No full-repository suite or remote CI result is claimed.

These raw logs and driver bytes are retained exactly for their receipt hashes; they are not product whitespace defects. The cached product/document check passed separately.
