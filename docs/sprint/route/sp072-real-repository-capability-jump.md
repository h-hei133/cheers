# SP072 Real Repository Capability Jump

## Goal

Prove real repository subdirectory development capability.

This task is failed unless the current system completes independent primary tasks on disposable copies of real project subdirectories with real source discovery, multi-file edits, failing commands, repair, targeted rerun, changed-file accounting, artifact or source proof, evidence proof, and result verdict.

This is not another small package pilot, transcript fixture, old diagnostic, catalog task, liveRun task, proof-only task, receipt-only task, or docs-only task.

## Required Tools

Use Serena MCP for owner discovery, symbol inspection, references, diagnostics, and targeted edits.

Use Spec-Driven Develop for requirement decomposition and coverage.

Use Superpowers where useful: systematic-debugging, test-driven-development, verification-before-completion, dispatching-parallel-agents, subagent-driven-development, and code review.

Use the provided playbook first, then local mature harness source after owner inspection. Inspect only task loop, harness, session trajectory, source discovery, repair iteration, verification rerun, artifact proof, and result reduction.

## Introduction Rule

Evaluate in order:

1. dependency use
2. structured port
3. isolated source adoption
4. behavior-only alignment

Structured port is expected. Isolated source adoption is preferred for small pure reducers, lifecycle transitions, safe codecs, failure classifiers, settlement helpers, or task-loop helpers when compatible.

Behavior-only alignment is fallback only and requires a written reason.

Do not copy names, paths, fields, user wording, terminal truth rules, or architecture wholesale.

## Required Primary Tasks

Create or update:

docs/sprint/real-repository-capability-jump.md

Define 4 independent primary tasks.

Rules:

- each task must be an independent diagnostic or executable case
- do not place all primary tasks inside one large test body
- at least 2 tasks must use disposable copies of current project subdirectories
- at least 1 task must be based on structured port or isolated source adoption from mature local harness inspection
- no task may recycle SP044 through SP071 primary tasks
- no toy single-file or tiny package task counts

Combined coverage must include:

1. at least 4 primary tasks execute
2. at least 3 tasks change 3 or more files
3. at least 2 tasks create or update targeted tests
4. at least 3 tasks start with real failing command output
5. at least 2 tasks complete after failed repair and second or third hypothesis
6. at least 1 task crosses replay or compact restore
7. at least 1 task produces artifact or source receipt proof
8. at least 1 task remains stopped_not_proven with exact missing proof
9. manual correction count is zero
10. false success count is zero

Existing diagnostics and SP071 package tasks are regression only.

## Product Fix Rule

If primary tasks expose product gaps, fix rightful owners only:

- runtime harness or trajectory
- execution seam or dispatch
- session, replay, or compact carry-forward
- source discovery
- repair flow or planner
- verification command
- artifacts
- tools feedback or policy
- evidence or result only as consumers

If no product gap appears, provide a strict no-change finding with primary task evidence.

Do not mark complete from old diagnostics, owner count, mission count, or documentation.

## Non-Substitution Rule

Do not substitute completion with:

- small package tasks
- one large test that hides multiple tasks
- old diagnostics
- transcript-only trials
- simulated files or command output
- proof-only or receipt-only changes
- docs-only or tests-only work
- evaluation-only behavior
- catalog or liveRun behavior
- provider or fallback success

If primary tasks do not perform real repository subdirectory development work, do not mark complete.

## Decision Rule

Final decision must be one of:

CONTINUE CURRENT PROJECT

Use only if primary tasks show repository subdirectory development capability and no critical product gap remains.

CONTINUE AFTER ONE FIX

Use only if scoped product gaps were fixed in this task and all hard gates pass afterward.

START MIGRATION COST SPIKE

Use if primary tasks fail because current architecture cannot perform real repository subdirectory development without broad rewrite.

## Live Provider Rule

Live provider is optional.

If live is run and fails only from provider-network, provider-config, provider-auth, or provider-unreachable after non-live gates pass, set status blocked. Report retest command, expected fields, failure class, why not product failure, git status, and uncommitted state. Do not retry live repeatedly.

Live output, provider success, or catalog success cannot replace primary task evidence.

## Naming And Safety

During development, product file names and product content must not contain process wording, comparison wording, reading-process wording, or outside project names. Use domain language only.

Evidence/result owns terminal truth. Do not claim success from provider output, tool execution, dry-run, apply, status, artifact existence, replay restore, compact summary, command output alone, transcript, trajectory entry, hypothesis, or quality counter.

Protect raw provider output, patch body, tokens, headers, secrets, private paths, and hidden reasoning. Do not manually read or print private provider configuration.

## Validation

Run primary repository tasks before and after fixes, focused changed-owner tests, SP044 through SP071 regressions, build, truthfulness gate, anti-false-success gate, diff checks, and live only if needed.

Commit only after hard gates pass. Push once only. If push fails, do not retry.
