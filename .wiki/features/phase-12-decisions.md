## 1. 贯穿本阶段的两条取舍

### 1.1 「声明与行为不一致」优先于「缺功能」

本阶段的可做项里，两类都有：

| 类型 | 例子 | 读代码的人会怎么想 |
|---|---|---|
| **声明与行为不一致** | T1：`Explore` 声明 `disallowedTools: ["write","edit"]`，**无人执行** | 「这个子代理不能改文件」——**错的** |
| **缺功能** | D1：子代理不跑 agent 循环 | 「子代理能力弱」——**对的** |

**前者优先**。理由：缺功能是**已知的边界**，声明不一致是**误导**。
`AGENTS.md` 要求「不得把失败伪装成成功态」，而**声明一个不存在的边界是同一类问题**。

**T1 因此排第一，且它是安全相关**——`Explore` 的定位是「只读探索」，
若它能 write，那么「派一个 Explore 去安全地看看」这个用法就是**假的**。

### 1.2 「绕过 provider 层」是**回归**，不只是缺陷

Phase 11 修了四项与 provider 层相关的能力（T2 流内 error、T4 失败分类、
T5 temperature 门控、T6 `budget_tokens`）。**这四项在 `task` 与 `/btw` 上全部无效**：

| Phase 11 修的 | `task` 是否受益 | 证据 |
|---|---|---|
| T5 temperature 门控 | ❌ | `taskTool.ts:160` 硬编码 `temperature: 0.3` |
| T6 `budget_tokens` | ❌ | 不发 `thinking` |
| T4 `failureClass` | ❌ | 只报 `The provider answered ${res.status}` |
| T2 流内 error 检测 | ❌ | 用非流式 `res.json()` |

**即**：Phase 11 的修复**有两条路径没覆盖**。
这正是复核轮 6 个缺陷的同一个共性（「修了一处，漏了兄弟」）的**放大版**——
这里是**整条调用路径**被漏掉。**T2 因此排第二。**

### 1.3 复核更正：**T1 单独做是空转**（`V8Decisions` 提出，主代理核实成立）

**子代理原判**：「T1 在 `taskTool` 不跑循环、不传工具的前提下，过滤的是**空集**。」

**主代理核实**：读 `taskTool.ts:148-162` 的请求体：

```js
body: JSON.stringify({
  model,
  messages: [ {role:"system",...}, {role:"user",...} ],
  temperature: 0.3,
}),                       // ← 没有 tools 字段
```

**`grep -n 'tools' taskTool.ts` 只命中 1 处，且是 `import type { ToolDefinition }`**。
即 **`task` 的子代理调用根本不传工具**——子代理**没有工具可用**。

**因此**：T1（「让声明的工具边界生效」）在**当前状态下过滤的是一个空集**，
`Explore` 声明 `disallowedTools: ["write","edit"]`，而子代理**本来就不能 write**——
不是因为它被拦住，是因为**它没有任何工具**。

**结论：T1 不能独立施工，必须与 D1 捆绑。**

| 旧排序 | 更正后 |
|---|---|
| T1（P0，独立）→ T2 → T3 → D1 | **T2**（P0，可独立）→ **T3** → **D1+T1 捆绑** → T4/T5 |

**为什么 T2 仍可独立**：它改的是**请求怎么发**（走 provider 层），
与子代理有没有工具无关——`/btw` 同样受益。

**为什么 T3 要在 D1 之前**：worktree 的自动合并语义在子代理**还不能改文件**时无害，
**一旦 D1 让它能改文件，自动合并就是「无审查地把改动并入主工作区」**。
所以 T3 是 D1 的**安全前置**。

**这修正了 §1.1 的推论**：原文说「声明与行为不一致优先于缺功能」——
方向对，但**在 T1 这个例子上，两者不可分离**：
只有先让子代理**有工具**（D1），才谈得上**限制工具**（T1）。

### 2.2 D2 — 数据驱动权限规则（含 deny）

> **复核更正（2026-09-26）**：本节原建议「只补 deny，不做路径/正则」，
> 并引用 pi 的哲学作为依据。**子代理 `V8Decisions` 指出两处问题，主代理核实后采纳其一、部分采纳其二。**

**更正一：引用 pi 的方式错了（采纳）。** 原文说「pi 反对的是靠审查保安全，
不是提供拒绝能力」——**这个解读把 pi 的论点窄化了**。读 pi `docs/security.md:1-20`：

> "Safety comes from limiting the files, credentials, processes, and network services Pi can
> access and affect if a generated action is wrong or hostile. **Watching the transcript, using
> project trust, and reviewing changes do not create a security boundary.**"

**pi 说的是「审查/信任/看记录都不构成安全边界」**，针对的是**prompt injection 与不可信代码**，
**它根本没有讨论「用户想配置拒绝某工具」这件事**。所以**用 pi 的哲学反对 deny 是错误引用**。
**pi 的立场对本裁决点中立**——它既不禁忌 deny，也不支持。

**更正二：路径级粒度不能省略（部分采纳）。** 原文说「不做路径/正则，收益不明确」。
**核实参考**：opencode 的规则**是** pattern 化的——

```ts
// packages/schema/src/v1/permission.ts:19-22
export const Rule = Schema.Struct({
  permission: Schema.String,
  pattern: Schema.String,      // ← 有 pattern
  action: Action,              // "allow" | "deny" | "ask"
})
```

**即参考的 deny 不是「禁用某工具」，是「禁用某工具在某 pattern 上的调用」。**
而用户真正想防的往往是**具体的高危目标**（`bash` 对某路径、`read` 对凭据文件），
**不是整个工具**——粗粒度的 deny 满足不了这个需求。**这一点原文用一句话跳过了，是真实取舍。**

**但仍保留「不做完整规则表」的结论**，理由改为：
① 完整规则表的主要成本在**匹配语义**（相对路径、符号链接、glob 方言）与**优先级规则**
   （allow 与 deny 同时命中时谁赢），这是**独立的复杂子系统**；
② 我们的 `evaluator.ts` **目前连 deny 的存储都没有**（`:156` 的 `deny` 只用于 plan 模式硬阻断），
   所以第一步不是做规则表，而是**让 deny 这个概念存在**；
③ 先做**最小可用的 deny**（工具级 + 可选 pattern），**实测用户是否真的需要 pattern**，
   再决定是否扩展到完整规则表。

**三个选项**（据更正后重写）：

| 选项 | 内容 | 成本 |
|---|---|---|
| **(a) 完整规则表** | 照参考：`{permission, pattern, action}` + 匹配语义 + 优先级 | **高** |
| **(b) 最小 deny** | `{tool, pattern?}` 的 deny 列表，**绕过免疫**，pattern 可选且支持简单的路径前缀 | **中** |
| **(c) 维持现状** | 承认「审查不构成安全边界」，精力放在进程/文件边界 | **零** |

**建议 (b)**。理由：
① 用户**确实需要「永远不许」的表达**——这是功能缺口，与 pi 的哲学**无关**（见更正一）；
② **保留 pattern**（可选、简单形式），因为参考证明了它有用（见更正二）；
③ 不做完整规则表，因为匹配语义与优先级是独立子系统，**应等实测证明需要再建**。

**若选 (b)，必须满足**：deny **绕过免疫**——不能通过审批被放行。
否则它就是一个「建议」，与 T1 要修的「声明不生效」是同一类问题。

### 2.3 D3 — `cheers.json` / `.agents/settings.json`

**决定性证据**（前置 §5.4）：这**不是「未被读取的配置」**，是**另一个 schema 的草稿**。

- 读取器的候选路径是 `config.json` 与 **`.cheers.json`（有点）**，
  **`cheers.json`（无点）不在其中**；
- 真实 schema 是**扁平**的（`.cheers.example.json`：`{"provider": "...", "maxTurns": 6}`），
  而 `cheers.json` 是**嵌套**的 `settings.v1`；
- **`model` 字段类型冲突**：读取器当**字符串**（`runtimeConfig.ts:72`），
  文件里是**对象**。**即使改名也无法解析。**

**逐字段核实**：`maxTurns`/`mcpServers`/`altScreen`/`showThinking` **都有实现**（用另一套 schema 表达）；
只有 `permissions.allowRules`（全仓 0 引用）与 `skills.directory`（`.codex/skills` 不存在）是空头支票。

**三个选项**：

| 选项 | 内容 |
|---|---|
| **(a) 删除两份** | 它们是零读者、逐字节重复、含外部项目名（`.codex/skills`）的**异 schema 草稿** |
| **(b) 实现 `settings.v1`** | 工作量中：一套新 schema + 读取器，其中 `allowRules` 与 `skills` **是未实现的功能** |
| **(c) 标记为草稿** | 保留但加注释。**留着不读的权威配置仍是误导** |

**建议 (a)**。理由：
① **不是「差一根线」**——schema 形状与字段类型都冲突，说明它是**另一份设计**；

## 10. 子代理派遣纪律（**本轮教训，写入流程**）

**本轮 8 次派遣：3 个成功、5 个失败**（其中 3 个 429 零产出、2 个成功）。

| 类型 | 任务形态 | 成功率 |
|---|---|---|
| **封闭式取证** | 「读这 N 个文件，回答这 M 个问题」 | **高**（`RefClaude`/`RefOpencode` 都成功） |
| **端点探测** | 一条命令 | **高**（`Probe` 17 秒） |
| **开放式探索** | 「探索 X 的现状」 | **零**（3 个全部 429，各 20+ 次调用后耗尽） |

**原因**：429 在 **20+ 次工具调用后触发**，开放式任务必然在产出结论前耗尽额度。

**纪律**：
1. 任务书**必须限定读取预算**（「最多读 N 个文件」）并**要求提前 yield**；
2. **开放式探索不派子代理**——主代理自己核实更快且不会被限流；
3. 子代理的结论**必须逐条核验**（本轮 1 条推翻了旧记录、6 条改变了裁决）；
4. **事实类与推理类复核要分开派**——`V7Claims`（事实，10/10 成立）
   与 `V8Decisions`（推理，6 条中 5 条有效）**各有各的价值**。
