# Route 200: Real provider task loop MVP

## Goal

Prove the first controlled real-provider task loop from user task to proposal, anchoring, confirmed apply, verification, and scorecard.

Routes 181-199 established:

- targeted context packet
- context graph and code graph trace
- task lifecycle
- task-driven context acquisition
- analysis quality gate
- plan quality gate
- real-provider anchored proposal smoke
- openai-compatible live provider adapter
- output validation
- anchoring
- exact-ready no-write proposal
- snapshot/recovery edit lanes
- verification command / repair-loop substrate
- harness scorecard and failure taxonomy

Route 199 proved that an explicit opt-in `openai-compatible` real provider can produce an exact-ready anchored no-write proposal.

Route 200 should now prove the next step:

controlled task loop MVP:

- controlled temp workspace
- explicit real-provider opt-in
- task lifecycle/context/analysis/plan
- real provider proposal
- output validation
- anchoring
- review/confirmation gate
- existing exact apply lane
- snapshot/recovery receipt
- verification/readback
- scorecard
- no broad mutation

This route should produce the first end-to-end evidence that the project can complete a small coding task under strict gates.

## Expected outcome

By the end of Route 200:

1. A controlled task fixture can run through read -> analyze -> plan -> proposal -> anchor -> review -> confirmed apply -> verify.
2. The proposal is generated by the real provider only under explicit opt-in.
3. The output is validated and anchored before any apply.
4. Apply occurs only after explicit confirmation in the controlled test/gate.
5. Apply reuses existing exact fenced / hunk-set apply lanes.
6. Workspace authority, stale-read, snapshot, recovery, journal, and verification boundaries remain intact.
7. Verification proves the file changed as expected using existing safe verification/readback mechanisms.
8. Scorecard records provider-called, anchor quality, apply result, verification result, and no broad mutation.
9. Failure path can stop at proposal, anchoring, confirmation, apply, verification, or repair eligibility with actionable reasons.
10. No direct provider-generated mutation, fuzzy apply, broad edit, new writer, default provider call, or provider call during apply is introduced.

### 1. Audit current task-loop gap

Before changing behavior, determine:

- whether any controlled real-provider path can currently apply an anchored proposal

### 2. Controlled task fixture

Add `realTaskLoopFixture.ts`.

Fixture requirements:

- temp workspace only
- one small source file
- one clear user task
- expected exact edit
- expected post-apply content
- no secrets
- no network dependency
- no external package dependency
- no production workspace mutation
- no command execution requirement unless existing allowlist already supports it

Initial fixture should be simple:

- source file: `src/smoke.ts`
- task: rename `startApp` to `runApp`
- expected edit: exact rename in function declaration and one call site if present
- verification: safe readback confirms expected text and absence of old text

### 4. Runtime task loop

Add `realTaskLoopRuntime.ts`.

Runtime flow:

1. create controlled temp fixture
2. build lifecycle/context/analysis/plan quality
3. run real provider anchored proposal only under explicit opt-in and readiness
4. validate output
5. anchor output
6. require explicit confirmation flag before apply
7. apply only through existing exact apply lane
8. capture snapshot/recovery/journal evidence
9. verify with safe readback or existing verification mechanism
10. build scorecard/result/session evidence
11. if verification fails, produce repair eligibility only; do not auto-repair

Default mode should run fake provider or safe skip depending verifier mode.

Real provider mode requires explicit opt-in.

### 5. Confirmation model

Add or reuse explicit confirmation state.

Rules:

- no apply without explicit confirmation
- confirmation is only valid for exact anchored proposal
- confirmation must reference anchored proposal id
- confirmation must reference fixture id / workspace authority
- confirmation does not bypass write route preconditions
- confirmation is test/gate-local, not global permission memory

### 6. Apply bridge

Use existing apply routes only.

Allowed:

- exact single-target anchored proposal -> existing fenced/hunk route
- exact hunk-set anchored proposal -> existing proposal hunk-set route

Disallowed:

- fuzzy apply
- broad apply
- provider output direct mutation
- new writer
- bypass stale-read
- bypass snapshot/recovery
- bypass post-write verification

### 7. Verification/readback

Use safe verification.

Preferred:

- readback verifies expected new text exists
- readback verifies old text absent when appropriate
- verification evidence includes file label, expected markers, actual result summary
- no raw full file dump

If using command verification, use existing allowlist only. Do not expand allowlist in this route.

### 11. Verifier script

Add `scripts/verify-real-provider-task-loop-mvp.mjs`.

Modes:

- default: fake provider or safe skip; no real provider call
- explicit real provider opt-in: run controlled live task loop
- explicit confirm apply flag: allow controlled fixture apply after exact anchoring
- no confirm: stop at review/confirmation required
- provider unavailable: structured skip
- verification failure: structured failure / repair eligible, no auto repair

Suggested env flags:

- `PRIVATE_AGENTS_REAL_PROVIDER_SMOKE=1`
- `PRIVATE_AGENTS_LIVE_TASK_LOOP_SMOKE=1`
- `PRIVATE_AGENTS_REAL_HOME=...`
- `PRIVATE_AGENTS_TEST_ROOT=...`
- `PRIVATE_AGENTS_CONFIRM_TASK_LOOP_APPLY=1`

Default validation must not set live provider or confirm apply.

### 12. Verifier coverage

Required deterministic coverage:

- default mode does not call provider and does not apply
- fake provider exact output can reach confirmation-required
- no confirmation stops before apply
- explicit confirmation applies through existing writer in temp workspace
- apply produces snapshot/recovery/journal evidence
- readback verification passes on controlled fixture
- verification failure path marks repair eligible but does not auto repair
- provider unavailable structured skip
- live provider output path shares report shape with fake path
- no raw provider output/full file content in result/session
- mutation authority never comes from provider output alone
- result-contract compatibility
