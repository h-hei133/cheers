# Risk Register

| Risk | Where it appears | Impact | Mitigation |
|---|---|---|---|
| Planning facts become terminal truth | Blocked plan returns, cross-file noop plan, degraded reopen fields, verify continuation fields. | `blocked`, `partial`, `not-proven`, `not-run`, or `skipped` could be presented as success later. | Keep `WorkflowTaskPlan` as pre-execution facts only; result/evidence owners classify terminal truth. Run result contract and Route221 gate for later behavior routes. |
| Command intent becomes command authority | `directCommand`, unsupported command, allowlisted command, verify continuation command. | Prompt text could imply command execution permission. | Keep command execution in `verification/commandStage.ts`; command planning emits blockers and requested command only. Preserve allowlist and blocked reason behavior. |
| Write/edit intent implies write authority | `write-file`/`edit-file` plans, mutation scope, replace directives, continuation repair plans. | Prompt or continuation facts could bypass workspace authority. | Keep workspace authority and mutation execution outside planning; future edit planning modules must return facts only. |
| Verify intent implies verification success | `verifyAfterEdit`, `verifyCommand`, verify continuation object, post-edit read-only verify cue. | Verification requested or planned could be reported as proven. | Verification execution and status remain in verification/result modules. Preserve `verifyAfterEdit=false` on read-only checks. |
| Repair intent implies repair success | Repair continuation, single-file repair recovery, cross-file converged noop. | Repair plan could be confused with applied repair. | Repair planning must not execute. Runtime/result must still distinguish applied, skipped, partial, failed, blocked, and not-proven. |
| Degraded/partial continuation upgrades to success | Degraded reopen candidates, previous remaining/failed targets, cross-file convergence. | False success after partial repair or ambiguous continuation. | Keep degraded fields explicit; do not collapse degraded/noop into success. Validate with Route221 anti-false-success gate when result/evidence routes touch this surface. |
| Inline permission facts imply authorization | `extractInlineContinuityContext` parses last approval and permission request fields. | A stale inline block could accidentally authorize a write or command. | Treat parsed approval/permission data as display/continuation facts only. Authority stays in policy/edit execution owners. |
| Context delivery output drifts into planning | Read/summarize/explain branches include read windows/fragments and context packet flags. | Planning could start constructing content or claiming read success. | Context modules may return read plan facts only; `context/readRuntimeStage.ts` owns delivery. |
| Evidence-string parsing remains scattered | Transform evidence and repair evidence parsing in `workflowTaskPlan.ts`. | Different parsers may disagree, weakening not-proven/partial semantics. | Centralize transform parsing in evidence/repair owners; preserve marker compatibility. |
| Filesystem checks inside planning hide runtime assumptions | `resolveContinuationReopenTarget` uses `fs.existsSync` and `fs.statSync`. | Candidate behavior can depend on current workspace state before execution. | Isolate in `repair/degradedReopenPlanning.ts`; keep read-only existence checks and explicit pruned reasons. |
| Target resolution drift | Target fallback, verify-tail stripping, mutation target selection, continuity target carryover. | Wrong file could be planned for read/edit/repair. | Characterize target decisions before extraction; preserve `targetPath`, `targetMissing`, and blocker wording. |
| Prompt regex overreach | Numerous English/Chinese weak cue regexes. | Generic prompts like "continue" could trigger edit or verify unexpectedly. | Keep weak cues gated by continuation state and owner-specific evidence. Add tests for conservative chat/read fallback. |
| Import cycles | Planning modules may import edit/repair/context/policy while those domains import `WorkflowTaskPlan`. | Build failures or ownership tangles. | Keep new modules returning plain plan facts. Avoid importing runtime stages. Use type-only imports where possible. |
| Planning directory becomes dumping bucket | Moving all predicates into `planning/workflowTaskPlanUtils.ts` or similar. | Monolith relocates instead of shrinking. | Use named destinations: intent, target, continuation, context, repair, verification, browser. |
| Dead predicate deletion risk | `hasContinuationStateSignalsInState`, `extractKeyTerms`, `isMutationInstructionFailure`, `uniqueStable`, `hashStableId`, over-exported rebind. | Removing a hidden behavior or external import could break runtime. | Delete only after `rg`, TypeScript build, and focused tests. Prefer move-with-caller until proven dead. |
| Compatibility export break | Runtime imports `buildWorkflowTaskPlan` and `extractInlineContinuityContext` from current path. | Coordinator breaks even if internals are correct. | Keep compatibility re-exports until runtime imports final owners. |
| Report/evidence anti-false-success drift | Later result/evidence routes may consume plan fields differently. | Route221 false-success gate could weaken. | This audit changes docs only. Future implementation touching result/evidence must run `verify:result-contract` and `verify:route221-anti-false-success-gate`. |

## Current Audit Risk Assessment

No runtime behavior changed in this route. The current risk is architectural concentration, not an observed behavior regression. The highest-risk future moves are repair/cross-file/degraded reopen planning and verification/command planning because both influence whether later runtime can truthfully classify stopped, blocked, partial, not-run, skipped, or not-proven outcomes.
