# Compatibility And History

Historical surfaces may remain reachable, but new product work must use current domain ownership and naming.

## Route History

- Route history may exist only under dev-history, evidence-history, route reports, or explicit compatibility surfaces.
- Do not create new route-numbered product files.
- Route-era names inside compatibility adapters must be deliberate and documented.
- New feature work must use current domain layout, not old route paths.

## Compatibility Surfaces

- Old aliases and historical reports must remain reachable until a dedicated retirement route removes them.
- Compatibility shims should delegate and re-export only.
- Compatibility shims must not gain business logic.
- If compatibility behavior needs real logic, move the logic into the current owning domain and keep the compatibility file thin.

## Historical Documents

- Project state and plan docs are not automatic truth.
- Historical reports can explain why a surface exists, but current code and current validation decide present behavior.
- Do not use historical names as evidence that a capability is currently supported.
