# Background wait progress and automatic promotion

Addition §17.3 calls for a cancellable wait with visible progress. The existing taskWait waited on the completion event correctly, but its live tool card had no progress body. This slice reuses ToolExecutionContext.onOutput and the existing tool.output/card path. After subscribing and rechecking the task, it displays elapsed wait time immediately and every five seconds. The clock describes this wait, not task completion percentage, the age of the task, or a running-state claim. A tick does not call get, replay process output or decide completion. Completion remains event driven; timeout and cancellation retain their original outcomes and do not stop the task.

No additional job store, runner, provider adapter or output event type is introduced. Progress is bounded by the existing 300-second cap and only installed when an output callback exists. The initial completion/abort checks happen before creating it. All settlement paths clear its timer; a progress observer failure disables further updates while preserving the actual task wait and final result. The emitted text contains only elapsed time and the wait limit, without command, task output, path or exception text. Existing tool-output persistence is retained; this is a bounded cadence, not a claim that progress writes are free.

Read-only comparison used the local oh-my-pi wait.ts:24–25,220–249: create a progress interval only for a supplied update callback and retire it together with the other wait resources. The target keeps its single-task event subscription and 300-second cap. It uses a five-second cadence because its text updates enter the existing tool-output path; it does not copy the reference's message/service coordination, 500ms snapshot polling, 30-minute cap or newer Promise.withResolvers API.
