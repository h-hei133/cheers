## 1. 贯穿本阶段的两条取舍

### 1.1 「声明与行为不一致」优先于「缺功能」

本阶段的可做项里，两类都有：

| 类型 | 例子 | 读代码的人会怎么想 |
|---|---|---|
| **声明与行为不一致** | T1：`Explore` 声明 `disallowedTools: ["write","edit"]`，**无人执行** | 「这个子代理不能改文件」——**错的** |
| **缺功能** | D1：子代理不跑 agent 循环 | 「子代理能力弱」——**对的** |

**前者优先**。理由：缺功能是**已知的边界**，声明不一致是**误导**。
`AGENTS.md` 要求「不得把失败伪装成成功态」，而**声明一个不存在的边界是同一类问题**。

**T1 因此排第一，且它是安全相关**——`Explore` 的定位是「只读探索」，
若它能 write，那么「派一个 Explore 去安全地看看」这个用法就是**假的**。

### 1.2 「绕过 provider 层」是**回归**，不只是缺陷

Phase 11 修了四项与 provider 层相关的能力（T2 流内 error、T4 失败分类、
T5 temperature 门控、T6 `budget_tokens`）。**这四项在 `task` 与 `/btw` 上全部无效**：

| Phase 11 修的 | `task` 是否受益 | 证据 |
|---|---|---|
| T5 temperature 门控 | ❌ | `taskTool.ts:160` 硬编码 `temperature: 0.3` |
| T6 `budget_tokens` | ❌ | 不发 `thinking` |
| T4 `failureClass` | ❌ | 只报 `The provider answered ${res.status}` |
| T2 流内 error 检测 | ❌ | 用非流式 `res.json()` |

**即**：Phase 11 的修复**有两条路径没覆盖**。
这正是复核轮 6 个缺陷的同一个共性（「修了一处，漏了兄弟」）的**放大版**——
这里是**整条调用路径**被漏掉。**T2 因此排第二。**

## 2. 需维护者裁决的点

> **格式**：**选项 + 建议 + 理由**。每项都基于 `phase-12-pre-research.md` 的实测证据。

### 2.1 D1 — 子代理是否改为真 agent

**新证据**（改变了工作量估计，见前置 §2.1、§2.5）：

- **`AgentCore` 侧已就绪**：`AgentLoopConfig.tools` **已经是参数**（`loop.ts:71`），
  `streamStep` **已经是注入**（`loop.ts:88-91`）。
- **真正的阻塞点**：`ToolExecutionContext` **没有 `tools` 字段**（`tools/types.ts:7-12`），
  所以 `task` 工具**在类型层面拿不到工具集**。
- **参考实现两边都是进程内**：Claude Code `tools/AgentTool/`（`runWithAgentContext`）、
  opencode `src/tool/task.ts`（Effect fiber + 子 session）。**pi 是子进程，但在 `examples/`**。
- **方案 B 需要新增 4 个对外参数**：`--model`/`--mode`/`--thinking`/`--append-system-prompt`
  （当前 0 命中），`--json` 已就绪。

**三个选项**：

| 选项 | 内容 | 成本 | 风险 |
|---|---|---|---|
| **(a) 完整方案 A** | 给 `ToolExecutionContext` 加工具集、`taskTool` 走 `runAgentLoop`、接上 worktree | **高** | 进程内共享状态；需处理权限边界 |
| **(b) 最小可信修复** | 只做 T1/T2/T3（边界生效、走 provider 层、worktree 语义） | **中** | 不解决「不是 agent」 |
| **(c) 先 (b) 再 (a)** | 分两轮 | 中 → 高 | — |

**建议 (c)**。理由：
① (b) 消除的是**误导**与**回归**，(a) 增加的是**能力**——前者优先；
② (a) 依赖 (b) 铺好的接缝：工具集可达、provider 层可用、worktree 语义安全，
   这三样不做好，(a) 会**在一个有缺陷的地基上盖楼**；
③ 分两轮让每轮都可独立验证——(b) 的验收是「声明的边界真的拦住了一次 write」，
   (a) 的验收是「子代理改的文件真的出现在 worktree 里」。

**若选 (a) 或 (c)，(a) 那轮的范围**：`ToolExecutionContext` 加 `tools`、
`taskTool` 用 `runAgentLoop`、让 `tools`/`disallowedTools`/`maxTurns` 生效、
把剩下 3 个死字段（`skills`/`effort`/`background`）**要么接上要么删除**。

### 2.2 D2 — 数据驱动权限规则（含 deny）

**冲突**：照参考做规则表，与 pi 的「进程边界才是安全边界」哲学相反
（pi `docs/security.md:1-17`）。

**但我们有一个参考都有、我们没有的东西**：**完全没有 deny 概念**。
`evaluator.ts` 的 `deny` **只用于 plan 模式的硬阻断**（`:156`），
**用户无法表达「永远不许用这个工具」**。参考实现都有：
Claude Code 有 `permissions` 规则表，opencode 有 `PermissionV1.Ruleset`
（`action: "deny"`，见前置 §2.6）。

**三个选项**：

| 选项 | 内容 | 成本 |
|---|---|---|
| **(a) 完整规则表** | 照 Claude Code：per-path/per-regex 的 allow/deny/ask | **高** |
| **(b) 只补 deny** | 加一个**绕过免疫**的 deny 列表（环境变量/配置），不做路径/正则 | **中** |
| **(c) 维持现状** | 承认「审查不构成安全边界」，精力放在进程/文件边界 | **零** |

**建议 (b)**。理由：
① 用户**确实需要一个「永远不许」的表达**——这是**功能缺口**，不是哲学分歧；
② pi 的立场是「审查不构成安全边界」，**这反对的是「靠审查保安全」，不是「提供拒绝能力」**；
   一个 deny 列表**不假装自己是安全边界**，它只是把「我不想让这个工具被调用」表达出来；
③ 完整规则表 (a) 的成本主要在**路径/正则匹配的语义**（相对路径、符号链接、glob 方言），
   而**收益不明确**——用户真正需要的是「别用这个工具」，不是「别用这个工具改这个文件」。

**若选 (b)，必须满足**：deny **绕过免疫**——不能通过审批被放行。
否则它就是一个「建议」，与 T1 要修的「声明不生效」是同一类问题。

### 2.3 D3 — `cheers.json` / `.agents/settings.json`

**决定性证据**（前置 §5.4）：这**不是「未被读取的配置」**，是**另一个 schema 的草稿**。

- 读取器的候选路径是 `config.json` 与 **`.cheers.json`（有点）**，
  **`cheers.json`（无点）不在其中**；
- 真实 schema 是**扁平**的（`.cheers.example.json`：`{"provider": "...", "maxTurns": 6}`），
  而 `cheers.json` 是**嵌套**的 `settings.v1`；
- **`model` 字段类型冲突**：读取器当**字符串**（`runtimeConfig.ts:72`），
  文件里是**对象**。**即使改名也无法解析。**

**逐字段核实**：`maxTurns`/`mcpServers`/`altScreen`/`showThinking` **都有实现**（用另一套 schema 表达）；
只有 `permissions.allowRules`（全仓 0 引用）与 `skills.directory`（`.codex/skills` 不存在）是空头支票。

**三个选项**：

| 选项 | 内容 |
|---|---|
| **(a) 删除两份** | 它们是零读者、逐字节重复、含外部项目名（`.codex/skills`）的**异 schema 草稿** |
| **(b) 实现 `settings.v1`** | 工作量中：一套新 schema + 读取器，其中 `allowRules` 与 `skills` **是未实现的功能** |
| **(c) 标记为草稿** | 保留但加注释。**留着不读的权威配置仍是误导** |

**建议 (a)**。理由：
① **不是「差一根线」**——schema 形状与字段类型都冲突，说明它是**另一份设计**；
② 删除**不会**删掉待实现的功能——`allowRules` 与 `skills` **从未按这个 schema 设计过**
   （D2 若选 (b) 会用**配置的**形式实现，不是这个文件）；
③ 留着会让用户以为改了有用——**静默失效的配置契约**，与 08 `T2` 的原始问题同类；
④ 含外部项目名且路径不存在，**违反 `AGENTS.md`**。

### 2.4 D4 — 压缩后恢复工作文件（M8）

**现状**：压缩**完全没有文件感知**（`compaction.ts` 无 `readCache`/`filesRead` 引用）。
丢掉的中间部分包含文件内容，模型在压缩后继续工作会**以为自己记得**。

**参考**（Claude Code `services/compact/compact.ts`）：保留最近 **5** 个文件、
每文件 **5000 token**、总预算 **50k**（`:122-124`），按时间戳倒序、排除已被保留的（`:1415-1445`）。

**三个选项**：

| 选项 | 内容 | 成本 | 风险 |
|---|---|---|---|
| **(a) 照参考** | 恢复最近 5 个文件的**内容**，带独立预算 | 中 | **与 T9 阈值直接冲突**：恢复撑大上下文 → 更早触发压缩 → 循环 |
| **(b) 只记文件名** | 压缩后插入「你之前读过这些文件」的**清单**，不含内容 | **低** | 模型还得重读；收益小但**零预算冲突** |
| **(c) 不做** | — | — | 模型压缩后缺上下文 |

**建议 (b) 起步，实测后再评估 (a)**。理由：
① (a) 与刚修的 T9 阈值**直接冲突**——参考用 50k 独立预算正说明**恢复必须有自己的预算**，
   而我们的阈值机制**没有这个概念**，引入需要同步改阈值；
② (b) 成本低、零冲突，且解决**最痛的部分**（模型不知道自己读过什么）；
③ **但要如实说**：本节**没有实测**「压缩后缺文件上下文」的频率与影响，
   (b) 的收益是**推定的**，不是实测的。**若维护者要求先有数据，应先做度量。**

### 2.5 D5 — 中途换模型（D11）

**现状**：`NextStepUpdate` **只携带 `messages`**（`loop.ts:66-68`），
`prepareNextStep` 因此**无法表达「下一步换个模型」**。

**但我们没有找到使用场景**：全仓无 `cheapModel`/`plannerModel`/`modelTier` 之类概念，
模型在会话创建时确定（`cliSessionRuntimeFactory.ts:121`）。

**两个选项**：

| 选项 | 内容 |
|---|---|
| **(a) 做** | `NextStepUpdate` 加 `model?` |
| **(b) 不做** | 承认换模型需重开会话 |

**建议 (b)**。理由：
① **没有证据表明我们需要它**——参考支持它，但我们的使用模式里没有这个需求；
② `AGENTS.md` 要求「不新增无法验证的表面」——(a) 加的是一个**没有调用方**的能力；
③ 若将来需要（例如引入「廉价规划 → 昂贵执行」），
   **那时再做**比现在做一个空的能力更符合「不为假设的需求写代码」。

**若维护者认为需要，请给出具体场景**（什么情况下必须在回合中途换），
否则 (a) 无法设计验收标准。

### 2.6 D6 — 后台命令执行（M2）

**本轮新证据**：`processTree.ts` **已经**具备参考的对应物——
全局 detached 子进程 PID 追踪、Windows `taskkill /T` 级联、
POSIX `process.kill(-pid, "SIGKILL")` 进程组级联、
以及 SIGINT/SIGTERM/SIGHUP/exit 的自动处理器（`:8-11`）。

**即「孤儿进程」这个担心已不成立。**

**但**：`ambientFacts.ts:9` 明述「the shell has no detached execution mode」，
**连计数器都不放**。引入后台执行要**推翻这条明述的立场**，
并需要配套的工具（列出/停止后台任务）与通知注入机制。

**建议不做**。理由：担心的风险（孤儿进程）**不存在**，
而真正的成本是**推翻既有立场 + 配套工具 + 通知机制**——这是**功能开发**而非缺陷修复，
且**没有用户需求证据**。**若需要，应单独立项并给出使用场景。**

## 5. 执行顺序

**前 3 项都是 P0**：T1 与 T3 是**安全**，T2 是**回归**。

先让边界生效，再让子代理能改文件，顺序反了会有一个窗口期。

## 6. 验证计划

### 6.1 每项都要「撤销修复 → 测试必须失败」

这是 Phase 11 的纪律，本阶段继续。**共 5 项，每项至少 1 个断言组。**

### 6.2 端到端验收（**不只跑单测**）

| 任务 | 端到端验收方式 |
|---|---|
| **T1** | 用真实工具注册表构造一个 `Explore` 子代理，**尝试 write**，必须被拒且**理由说明是子代理边界** |
| **T2** | 让 `task` 发一次真实请求，断言它**经过 provider 层**（例如 `compat` 生效、`failureClass` 被填） |
| **T3** | 在 worktree 里造一个改动，释放后断言：**目录被保留**、**路径被回报**、**主工作区未被自动修改** |
| **T4** | 到达步数上限时，断言**请求里带了一条说明**（而不是静默 `tool_choice: none`） |
| **T5** | 两个协议在 `allowTools: false` 下**产生一致的可观察行为** |

## 7. 风险登记

| 风险 | 触发条件 | 缓解 |
|---|---|---|
| **T1 的边界生效后，既有用法被拒** | 若某处依赖「Explore 能 write」（不该存在） | 先跑全量套件，看是否有测试因此失败；失败的测试**逐个判断是断言错了还是行为错了** |
| **T2 改走 provider 层后行为变化** | `task` 的请求形状会变（`compat`/`temperature` 门控生效） | 这是**期望的变化**；但需确认没有依赖旧形状的测试 |
| **T3 改语义后 worktree 堆积** | 保留而不删除 → 目录累积 | 参考的做法是**回报路径由父代理决定**；需确认我们的 `/worktree` 类命令能清理 |
| **T4 的告知文案被模型忽略** | 提示词注入不保证生效 | 如实记录：**告知 ≠ 保证**；若实测无效，应改用更强的机制或放弃 |
| **子代理端点 429** | 派遣量超过限流 | 任务书**限定读取预算**并要求**提前 yield**（Phase 11 复核轮的教训） |
