# 参考仓对照：`pi` 是否可作为架构重写目标（2026-09-18）

> 起因：提议"既然 `pi` 明显更干净、可维护性极高，为什么不直接学它的架构，把我们的重构为这种形式"。
> **本文件是可行性分析，零代码改动。**
>
> **方法学声明（重要）**：第一轮分析用**本仓自定的规则**（0 环、≤20 名模块上限）
> 去评判 `pi`，被判为**循环论证**——那两条是 NormProof 的规定，不构成业内共识，
> 且 NormProof 本身是**进行中**的项目。**故本文件重做，只用不依赖我们规则的角度。**

## 0. 规模与历史（先确认两者可比）

| | 我们 | `pi` |
|---|---:|---:|
| 包 | 4（1 个真包 + python-eval 隔离） | **11** |
| 生产 `.ts` | 960 | 832 |
| 测试 `.ts` | 520 | 573 |
| 生产代码行 | **177,262** | 163,253 |
| `.md` 文件 | **1,134**（`docs/` 770 + 其余 364） | **113** |
| commit 数 | 1,599 | **6,421** |
| 开发时长 | 5 个月（2026-04-11 起） | **13 个月**（2025-08-09 起） |

**代码量相当，但 `pi` 的 commit 数是我们 4 倍** —— 它高频小步，我们 route 式大步。
我们的 `docs/` 体量是它的 **10 倍**，这是开发方式的产物，不是架构差异。

## 1. 角度一：`pi` 是**发布的库族**，我们是**单一应用**（最根本的差异）

| 包 | 发布状态 | 版本 | 依赖数 |
|---|---|---|---:|
| `@earendil-works/pi-ai` | **public** | 0.85.1 | 10 |
| `@earendil-works/pi-tui` | **public** | 0.85.1 | 2 |
| `@earendil-works/pi-protocol` | **public** | 0.85.1 | 2 |
| `@earendil-works/pi-agent-core` | **public** | 0.85.1 | 7 |
| `@earendil-works/chord` | **public** | 0.85.1 | 1 |
| `@earendil-works/pi-durable` | **public** | 0.85.1 | 2 |
| `@earendil-works/pi-client` | **public** | 0.85.1 | 2 |
| `@earendil-works/pi-coding-agent` | **public** | 0.85.1 | 19 |
| `@earendil-works/pi-server` | **public** | 0.85.1 | 3 |
| `@earendil-works/pi-telemetry` | **public** | 0.85.1 | 0 |
| `@earendil-works/pi-evals` | private | 0.85.1 | 0 |

**11 个包中有 10 个 `private: false`，统一 0.85.1 版本，全部发布到 npm。**

**这是 `pi` 包布局的成因**：`pi-tui` 要被外部当库用，所以它**不能**依赖 `coding-agent`；
`pi-ai` 要独立发布，所以 provider 适配器必须收在自己包里；
`chord` 是"应用组合运行时"，所以它是别的包的基础。

**推论**：`pi` 的 `packages/` 边界首先是**公开 API 边界 + 独立版本边界**，
**不是**内部可维护性边界。我们**没有这个约束**——`ts-shell` 没有外部消费者。
照搬 11 包布局，在无外部消费者时会得到**发布开销**（semver、跨包类型、构建编排、依赖解析），
而得不到它存在的理由。

## 2. 角度二：`pi` 的结构本身**比我们松**（不依赖我们规则的项）

| 指标 | 我们 | `pi` |
|---|---:|---:|
| 循环依赖 | **0** | **10**（最大 **32 文件**） |
| 超过 20 个函数名的模块 | 12 | **75** |
| 最大模块 | 52 函数 | **204 函数 / 6,649 行** |
| 模块行数 p90 / max | — | 545 / **6,649** |
| `tsconfig` `strict` | ❌ **未设置** | ✅ **`true`** |
| `: any` / `as any` | 7 / 22 | 22 / 41 |
| `@ts-ignore`/`@ts-expect-error` | **0** / **0** | 0 / 0 |
| 非空断言 `!.` | 126 | 63 |

**关于"0 环"的诚实说明**：我一开始把它当作判定依据，你指出那是我们自定规则。
**但 `pi` 的环是真实的**（已核实非 barrel 假阳性）：

- `pico3/types.ts:28` → `./system.ts`，而 `system.ts:15` → `./types.ts`（真实双向）
- `server/types.ts:3` → `./listener.ts`，`listener.ts:1` → `./connection.ts`，`connection.ts:4` → `./types.ts`（真实三角）

`pi` 的环里 **3 个横跨 `core/`**（24 / 21 / 20 文件级）。
而 `pi` **没有任何文档定义 `core/` 的准入标准**（`grep` 其 `AGENTS.md`、`CONTRIBUTING.md`、
无 ADR、无架构文档）——**这说明"不定义 `core/`"与"产生环"是相关的**。

**`strict` 是唯一"与我们的规则无关、且 `pi` 明确做得更好"的项** —— 见 §4。

## 3. 角度三：`pi` 干净的是**视野**，不是**结构**

前两轮我展示的 `pi` 优点，逐条归因：

| `pi` 的表面优点 | 真实归因 |
|---|---|
| `test/` 与 `src/` 分层，544 个测试全在 `src/` 外 | **目录约定**，非架构。可学（见 §5） |
| `AGENTS.md`（124 行）路径引用全部有效 | **它从未累积**——113 份 `.md`、无 `DOC_STATUS`、无 route 时代文档。**不是"检测漂移"的机制**，只是还没走到那一步 |
| 包边界清楚 | **发布约束的副产品**（要被外部消费就不能乱依赖），不是主动设计 |
| 顶层目录只有 12 个（跨 11 包） | 因为**大部分代码在别的包里**；单看 `coding-agent` 也有 8 个子目录 |

## 4. 角度四：变更局部性 —— **两者同量级**（这是"开发是否顺手"最直接的代理）

| 指标（近 300 个非 merge commit） | 我们 | `pi` |
|---|---:|---:|
| 每 commit 触碰文件数 p50 | 4 | 4 |
| 每 commit 触碰文件数 mean / max | 13.4 / 576 | **8.9** / 165 |
| **传递 fan-in**（改一个叶子模块波及的文件数）p50 | 10 | **6** |
| 传递 fan-in p90 / max | 64 / 254 | 72 / **172** |
| fan-in > 30 的模块数 | 191 / 899 | **127 / 666** |

**`pi` 略好，但差距不足以支撑"推倒重来"。** p50 完全相同（4 个文件/commit），
p90 甚至我们更低（22 vs 25）。

## 5. 结论

### 不推荐照搬 `pi` 架构

| 理由 | 依据 |
|---|---|
| **① 根本约束不同** | `pi` 的 11 包布局由"发布 10 个独立库"决定（§1）。我们是单应用，搬过来只有发布开销 |
| **② 它并非更优结构** | 10 个环、75 处越界、6,649 行巨型模块（§2） |
| **③ 其优点主要是视野而非结构** | 归因于开发方式与规模，非架构（§3） |
| **④ 变更局部性同量级** | 直接代理指标显示无实质差距（§4） |

**最根本的一点**：我们的 770 份 `docs/`、route 命名、30 个顶层目录，
是 **5 个月 route 式开发（1,599 commits / 177k 行）**的产物。
`pi` 的"干净"来自 **13 个月高频小步（6,421 commits）** 且无 route 阶段。
**照搬目录布局不会改变开发方式**，漂移会以同样方式重新累积。

### 但有三项**局部实践**值得吸收

| 项 | 价值 | 依赖我们的规则？ |
|---|---|---|
| **`tsconfig` 开 `strict`** | ⭐ **最高** —— `pi` 做了我们没做 | **否**（TS 工具链自带严格性） |
| `test/` 与 `src/` 分层，且 `test/` 自带 `fixtures/` 与共享基建 | 中 —— 能让"哪些文件不该发布"从文件名启发式变成目录规则 | 否 |
| `check:*` 类门禁的检查项（`check:ts-imports`、`check:entry-graphs`、`check:runtime-deps`） | 中 —— 与我们既有 25 个 `verify-*.mjs` **同构**，可借鉴检查项 | 否 |

**这三项都不需要重构架构即可采纳。**

### 对既有结论的修正

**`architecture-exploration-2026-09-18.md` §4 的"不应分离测试"结论需修正**：
我当时给出的硬障碍理由（`longSessionDurability.test.ts` 的动态路径需"先改造再搬迁"）
**不成立** —— `pi` 的 `test/` **同时容纳夹具与共享基建**（`fixtures/`、`suite/harness.ts` 都在 `test/` 内），
因此那条路径只是**同一次搬迁里的一行改动**，不存在先后依赖。

**修正后的准确表述**：
- **技术上可分离**，且 `pi` 是 11 个包的全仓反例；
- **`pi` 的形态是"按主题组织"而非"镜像 `src/` 路径"** —— 免去新增测试时维护镜像路径；
- **是否做仍是风格决策**（规则明文允许并排并给出并排示例），但**我原来的反对理由已撤回**。
